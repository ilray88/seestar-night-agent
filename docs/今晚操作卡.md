### 19:26–19:34 那次崩溃的真相（已查明，非代码缺陷）

当时 4 次「异常退出，代码 -1」，间隔正好 2–3 分钟。根因不是运行器有 bug：

1. `events.jsonl` 里**没有任何 `kind:"crash"` 记录**。若真抛异常，一定会写下 traceback。
2. 退出码 `-1` = `0xFFFFFFFF`，在 Windows 上表示**进程被外部强制终止**，来不及写日志。
3. 时间间隔 2–3 分钟，正好等于我当时那几条诊断命令的 **120 秒 shell 超时**。超时会杀掉整棵进程树，连带当时还挂在 opencode shell 下的 watchdog 和 runner。

**结论：是我自己的诊断命令导致的，不是运行器的问题。** 而且防护生效了——`_already_running()` 每次都识别出「M31 已在叠加 N 帧」直接续拍，131 帧一帧没丢。

但也因此暴露了一个真实隐患，已修：原来的 `maxAttempts = 3` 太脆——整夜 10 小时只要撞上 3 次偶发崩溃，watchdog 就放弃，后面几小时全作废。**现改为无限重启 + 指数退避（60s→最长 300s），直到 05:30。**

自查一条命令（不碰设备状态）：

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe' or Name='powershell.exe'" |
  Where-Object { $_.CommandLine -match 'night_runner|night_watchdog' } |
  ForEach-Object { "pid=$($_.ProcessId) ppid=$($_.ParentProcessId) $($_.Name)" }
```

正常应只有 3 个进程：`powershell(night_watchdog)` → `python(night_runner)` 父进程链。**若看到两套，说明有孤儿进程，用 `Stop-Process -Id <旧pid> -Force` 清掉旧的**，否则两个 runner 会互相抢设备。

手动 park：

```powershell
.\seestar-mcp\.venv\Scripts\python.exe -c "import sys; sys.path.insert(0,'scripts'); import night_runner as NR; NR.native('scope_park', timeout=120)"
```
