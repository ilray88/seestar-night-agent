# 用 AI Agent 全权托管一台 Seestar S30 Pro，一夜拍下 8 个深空目标

> 设备：ZWO Seestar S30 Pro（固件 9.75）
> 地点：深圳龙华市区，东北向窗外约 1㎡ 的平台
> 时间：2026-10-19 19:15 → 2026-10-20 05:15
> 结果：8 个目标全部完成，合计 391 分钟有效曝光，05:15:51 自动折叠收工，零告警

---

## 一、背景：一个很受限的机位

先说清楚限制条件，因为后面所有的设计都是被这些条件逼出来的。

**观测窗口极窄。** 设备架在东北向窗外的平台上，只有一段 **方位角 330° → 110°**（跨正北，宽 140°）的天区可见，最低高度 20°。这意味着：

- 天一黑能拍的目标，半夜会转出窗口
- 半夜升起的目标，要等它转到窗口里
- 大部分时间窗口里只有 2～3 个可选目标

**市区光害。** 深圳龙华，楼下就是路灯和住宅楼。目视极限星等大约 3.5～4 等。

**供电线从上方垂下。** 为了不缠绕，线是吊在上面的，留了余量。但这也意味着**方位角不能无限单向转**，否则线会绞紧。整夜的净旋转必须控制住。

**无人值守。** 我睡觉，它自己拍。这意味着程序必须能自己判断天气、自己处理异常、自己收工。

---

## 二、系统架构：AI Agent 怎么控制望远镜

Seestar 官方 App 在手机上，不适合做整夜编排。我用的是开源方案：

```
AI Agent（写计划、盯状态、处置异常）
    ↓
seestar-mcp（34 个 MCP 工具）
    ↓
Alpaca 协议 127.0.0.1:5555
    ↓
seestar_alp（开源后端）
    ↓
设备 JSON-RPC（端口 4700）
```

三个关键细节：

1. **Alpaca 的 device_num 是 1，不是 0**。这个坑我卡了很久。
2. **固件 7.18+ 需要 RSA 互操作密钥**，否则连不上。密钥可以从官方 XAPK 里提取（`seestar_client_key.pem`）。
3. **设备只允许单一 TCP 连接**。后端在线时你直接探测 4700 必然超时，这是正常现象，别以为设备挂了。

**进程链与 AI 解耦。** 这是最关键的设计：

```
svchost → powershell night_watchdog.ps1 → python night_runner.py
```

AI 只负责「写计划」和「事后处置」，实际执行挂在 Windows 计划任务下。**关掉 AI 会话，拍摄照常进行。** 三层守护：

- `night_runner.py`：主运行器，自己判断硬停条件
- `night_watchdog.ps1`：进程守护，崩了自动重启（幂等，不会重复开叠）
- `night_monitor.py`：每分钟独立巡检，82°C 兜底强制折叠

## 三、观测计划：怎么排 8 个目标

窗口是跨正北的（330°→110°），我用 astropy 把所有候选目标在窗口内的可见区间扫了一遍，按「方位角单调移动」来排序，尽量让望远镜少来回转。

最终计划（8 个时段，原计划 585 分钟）：

| 时间 | 目标 | 类型 | 滤镜 | 单帧 |
|---|---|---|---|---|
| 19:15–20:45 | M31 仙女座大星系 | 旋涡星系 | IRCUT | 10s |
| 20:50–22:05 | IC1805 心脏星云 | 发射星云 | LP | 20s |
| 22:10–23:25 | NGC1499 加州星云 | 发射星云 | LP | 20s |
| 23:30–00:45 | M45 昴星团 | 星团+反射星云 | IRCUT | 10s |
| **00:45–02:20** | **IC405 火焰星云** | 发射星云 | LP | 20s |
| **02:20–03:35** | **IC443 水母星云** | 超新星遗迹 | LP | 20s |
| 03:35–04:55 | M81 波德星系 | 旋涡星系 | IRCUT | 10s |
| 04:55–05:15 | NGC2403 | 旋涡星系 | IRCUT | 10s |

**电缆预算**：整夜净方位角旋转 **−15.5°**，远低于 200° 限位。注意是**净旋转**（带符号累加），不是绝对行程——因为目标之间来回摆，绝对行程有 219°，但净旋转很小，线不会绞。

**拍摄顺序原则**：
- 发射星云用 LP（光害）滤镜 + 20 秒，压住城市光害、保留 Hα
- 星系/星团用 IRCUT + 10 秒，保留宽带的颜色
- 天亮前留 30 分钟收尾余量（05:15 停拍，05:30 强制折叠）

## 四、临时改计划：把「空档」填成最好的两张

原计划里，**00:45–03:05 是留空的**——因为当时的天气预报显示这段总云量 85～97%，判断不可拍。

实际那晚我用 open-meteo 拉了逐小时数据，发现：

| 时间 | 总云量 | **低云** | 高云 | 降水 |
|---|---|---|---|---|
| 21:00 | 80% | **0%** | 80% | 0% |
| 22:00 | 90% | **0%** | 90% | 0% |
| 23:00 | 93% | **0%** | 93% | 0% |
| 00:00 | 96% | **1%** | 96% | 0% |
| 01:00–03:00 | 95–97% | **0%** | 95–97% | 0% |
| 04:00 | 87% | **4%** | 86% | 0% |
| 05:00 | 32% | **2%** | 31% | 0% |

**低云整夜 0–4%，降水全程 0%。那 95% 全是高空卷云。**

卷云会降对比度、增加散射，但**不遮星**。对深空摄影来说，它该死但不是致命的；真正致命的是低云和降水。

于是我把判据改了：

```
降水概率 ≥ 60%  → 停
低云 ≥ 70%      → 停（低云遮挡星空）
总云量 ≥ 98%    → 停（几乎全遮）
否则            → 继续拍
```

改完之后，原计划停拍的空档变成了整夜低云最低的黄金时段。我用 astropy 重扫窗口内可见目标，填进了 **IC405 火焰星云**和 **IC443 水母星云**——御夫座/双子座的发射星云，方位角 54°～87°，高度 48°～73°，完美在窗。

**结果这两张成了全晚质量最好的发射星云。** 因为它们刚好赶上「开拍后设滤镜」那个 bug 修复完成（见下）。

## 五、三个坑（本篇最想分享的部分）

这三个 bug 有个共同特征：**设备返回「成功」，但实际没生效。** 如果不做地面真相校验，你根本发现不了，只会觉得「今晚拍得不好」。

### 坑 1｜天气停止 → 监工无限重启 → 机械臂反复起落

**现象**：22:11 切到 NGC1499，天气判定不可拍 → 停拍折叠 → 收工。看起来一切正常。但 5 分钟后它自己又启动了，又 goto 回 NGC1499，又判定不可拍，又折叠。如此循环。

**根因**：运行器当天气不好时是「正常退出」（返回码 0）。watchdog 正确地结束了。但每分钟巡检的 monitor 看到「心跳中断 + 任务未运行」，以为是崩溃，于是 `schtasks /End + /Run` 重启。

**修复**：
- 运行器正常收尾时写一个 `STOPPED` 标记文件，watchdog 和 monitor 见到就不重启
- 天气不好不再「终止整晚」，改成「折叠等待」：park → 每 5 分钟复查天气 → 转好就重试本时段，转不好就到本时段结束
- goto **之前**先做天气预检，避免「先转 120° 再发现不能拍」

这一条对机械寿命很重要。那一晚来回起落了 3 次，本来是完全没必要的心智损耗。

### 坑 2｜曝光设置静默失败（code 259）

**现象**：日志写着「曝光 -> 20s」，但 FITS 头里是 `EXPTIME=10.0`。滤镜也一样，日志写 LP，文件名写 IRCUT。

**根因**：设备在叠加运行中**拒绝改曝光**，返回：

```json
{"error": "stack is already running", "code": 259}
```

但这个错误**藏在 `Value.error` 里**，而外层 `result` 和 `ErrorNumber` 都是 0。旧代码只看「有没有抛异常」，所以永远不报错。

**修复**：

```
1. 先 get_view_state，若 state == "working" → iscope_stop_view ["Stack"]
2. 轮询 15×2s，等 state 离开 working
3. set_setting {exp_ms: {stack_l: 20000, continuous: 500}}
4. 读回 get_device_state.setting.exp_ms.stack_l 校验
5. 不匹配就重试（最多 4 次），匹配才认成功
```

**教训**：**永远不要相信「调用没抛异常」就等于成功。** 一定要读回校验。

### 坑 3｜滤镜会被 `iscope_start_stack` 重置（最隐蔽）

**现象**：设了 LP 滤镜，读回是 2，一切正常。一开拍，又变成 IRCUT 了。整晚 8 个目标的文件名全是 `IRCUT`，包括本该用 LP 的发射星云。

我做了三轮实验才确认：

| 实验 | 结果 |
|---|---|
| 停止叠加时设 wheel=2 | 读回 2，能稳定保持 30 秒 ✓ |
| 然后 `iscope_start_stack` | 立刻变回 1 (IRCUT) ✗ |
| **开拍之后（state=working）再设 wheel=2** | **保持 42 秒，叠加继续推进 ✓** |

**结论：`iscope_start_stack` 会把滤镜轮重置为 1（IRCUT），无论你之前设成什么。唯一有效的顺序是：先开拍，等 state=working，再设滤镜。**

**修复**：把「1) 设滤镜」整块挪到「5) 开拍」之后，变成「5b) 设滤镜」，加读回校验 + 最多 4 次重试。

**地面真相验证**：设备里子帧文件名从

```
Light_IC405_20.0s_IRCUT_20261020-005144
```

变成

```
Light_IC405_20.0s_LP_20261020-005716
```

这才叫真的生效了。

顺便说：`get_albums` 返回的 `thn` 字段里带着真实滤镜名，是我发现这个问题最快的途径。**检查滤镜有没有生效，别信日志，去看设备文件名。**

## 六、其他运维细节

**防过温。** S30 Pro 没有制冷，CCD 温度常年在 38～41°C，热噪声是主要噪声来源。整夜实测机身温度在 **40～59°C** 之间震荡（叠加/写入负载起伏导致），阈值设在 80°C，82°C 由独立巡检兜底强制折叠。`is_overtemp` 全程 false。

**防断连。** 心跳超过 10 分钟未更新就判定断连，折叠等待。

**防休眠。** Windows 侧 `powercfg` 把所有 AC 超时设为 0，否则拍一半电脑睡了。

**远程查看。** RDP 3389 + ZeroTier，手机能随时连回来看进度。

**电量。** 全程 100%，插电运行，低于 20% 会保护性停机。

**窗口坐标必须与设备 GPS 一致。** 地平遮罩是按 site_profile 算的，坐标不一致会导致「以为能拍其实被楼挡住」。

## 八、后期处理：为什么一定要用 FITS

这是我想强调的第二件事。

**设备机内直出的 JPG，动态范围只用了 13～31 个灰阶层（满值 255）。** 也就是说，相机自带的拉伸极其保守，把 90% 的信息压掉了。

但设备同时存着一份 **16-bit 叠加原片（`.fit`，47.5 MB）**，65536 级、无损。这才是真正的素材。

我写了一个 Python 后期流程（numpy + PIL，没装 siril/pixinsight）：

```
1. 手写 FITS 解析（BITPIX=16, BZERO=32768, big-endian）
2. 逐通道多项式背景扣除（注意：不能 clip 负值，否则 median 塌成 0，MTF 会退化）
3. 颜色平衡（逐通道 p99.9，可调强度 cb，发射星云要设 0）
4. 拉伸前亮度降噪（传感器无制冷，热噪声大）
5. 鲁棒黑/白点（median - 2.8σ / p99.9 × 系数）
6. Reinhard 色调映射 + 解析求解 MTF 中值
7. 饱和度 → 色度降噪 → 反锐化 → sRGB
```

**效果对比（动态范围，p99 − median）：**

| 目标 | 机内 JPG | 后期 | 提升 |
|---|---|---|---|
| IC1805 | 17 | **42** | +147% |
| NGC1499 | 13 | **28** | +115% |
| M31 | 19 | **29** | +53% |
| M45 | 24 | **35** | +46% |
| IC405 | 31 | **44** | +42% |
| M81 | 16 | **21** | +31% |
| NGC2403 | 14 | **18** | +29% |
| IC443 | 16 | **20** | +25% |

**两个后期上的坑：**

1. **背景多项式会吃掉大星云。** IC1805 心脏星云跨度约 1000 px，用 3 阶多项式拟合背景时，整个星云被当成「梯度」减掉了。发射星云要改成 `deg=1, grid=32`。
2. **白平衡会压制 Hα。** 逐通道 p99.9 白平衡会把红色通道乘 0.845，而发射星云恰恰是红光主导。所以发射星云必须 `cb=0`（关掉色彩平衡）。

## 九、复盘：哪些做对了，哪些没做好

### 做对的

1. **低云判据**。如果沿用人云亦云的总云量，那一晚基本拍不了 20 分钟。改成低云为主后，整夜可用。
2. **填坑**。原计划空档 00:45–03:05，实测那是最好的窗口。加的两个目标成了全晚最佳。
3. **三层守护 + STOPPED 门控**。无人值守最怕的不是设备坏，是程序陷入震荡。
4. **FITS 后期**。动态范围提升 25%～147%，这是纯软件能拿到的最大收益。
5. **先开拍后设滤镜**。这个顺序搞反了，一整晚的发射星云全废。

### 没做好的

1. **滤镜 bug 踩了太久**。前 4 个目标（M31、IC1805、NGC1499、M45）全部用错滤镜。IC1805 和 NGC1499 这两个发射星云损失最大，基本需要重拍。
2. **两处 gain 与计划不符**（IC1805、M45 都是 200 而非 80）。这是「曝光修复」上线前旧会话遗留的，当时没有做参数校验。
3. **物理调平没做**。设备实测倾斜 4.1°，罗盘未校准（`cali:0, stable:0`，方向值乱跳）。这会导致指向误差和更高的丢帧率——虽然那晚丢弃帧是 0，但这是运气。
4. **NGC2403 只给了 20 分钟**（74 帧）。为了让前面填坑的目标有时间，把它压缩得很厉害，数据偏薄。

## 十、下次改进

1. **重拍 IC1805 和 NGC1499**，用 LP + 20s + gain 80，各 75 分钟。这两个是本季最该出图的目标。
2. **调平三脚架 + 校准罗盘**。这是减少废帧最直接的物理手段。
3. **参数校验前置**。每个时段开拍后，读回曝光、增益、滤镜三项，全部核对计划，不一致就重试。不要等事后看 FITS 头才发现。
4. **把 FITS 头写入计划值作为断言**。设备实际值和计划值都记下来，事后能一眼看出偏差。
5. **NGC2403 单独给它一晚**，或者至少 60 分钟。

## 十一、一点感想

这台设备 30mm 口径、3000 多块钱，放在市区的窗台上。它拍不到哈勃那种图，但它能让你真的看见——

254 万光年外的星系盘上，尘埃带是暗的；
7500 光年外的氢气体，红得像在燃烧；
5000 光年外一颗恒星三万年前炸开，留下的丝状物还在扩散。

而这一切发生在你睡觉的时候。

技术上的坑挺多，但踩完之后，一个晚上能拿下 8 个目标、6.5 小时曝光。这个门槛比想象中低，也比想象中有意思。
